## Pull

Pull → get the latest changes from GitHub:

Fetches new commits from remote and merges them into our current branch.

```bash
git pull
```

Fetch without merging (just download changes). Fetch downloads and commits to our local repo, but doesn’t change our working files. Use this to see new remote changes before merging manually.

```bash
git fetch
```

## Clone_Repositories

Clone is copying a GitHub repo to our local machine. Creates a folder with the repo files. Sets up origin automatically (remote).

```bash
git clone https://github.com/username/repo.git my_folder_name  # (folder name optional)
```

```bash
git remote -v
```

Output:

```text
origin  https://github.com/username/repo.git (fetch)
origin  https://github.com/username/repo.git (push)
```

## Fork_vs_Clone_(GitHub)

Clone, copies someone else’s repo as-is to our local machine. We can edit locally but don’t have write access to the original repo.

```bash
git clone https://github.com/otheruser/project.git
```

Fork, creates our own copy of someone else’s GitHub repo in our account. We can push to our fork freely. Often used in open-source contributions:

- Fork the repo on GitHub.
- Clone our fork locally.
- Make changes → push to our fork → open a PR to the original repo.

---
## Fork_in_Detail

When we fork a repository, we create a server-side copy of someone else's project under our own GitHub account. This allows us to make changes and push them to our fork, even though we don’t have permission to push directly to the original (upstream) repository.

```text
🔁 Fork = "I want my own online copy to modify and share."
```

In contrast:

```text
💾 Clone = "I want a local copy on my computer to view or edit."
```

We can clone any repo, but without write access, we cannot push our changes back to the original. Forking solves this by giving us a remote repository (on **GitHub**) that we do control.

After forking and cloning the fork locally, we can:

- Make changes
- Commit and push them to our fork
- Open a Pull Request (PR) from our fork to the original repo

This allows project maintainers to review, discuss, and merge our contributions. Example workflow:

```bash
git clone https://github.com/your-username/repo-fork.git  # Clone your fork
cd repo-fork
git remote add upstream https://github.com/original-owner/repo.git  # Track original
git checkout -b feature/add-login  # Create feature branch
# ... make changes ...
git add .
git commit -m "Add login functionality"
git push origin feature/add-login  # Push to your fork
```

Then open PR via GitHub UI

A fork is an independent project. We can:

- Run CI/CD pipelines
- Host documentation
- Accept contributions to our version

This is useful if:

- The original project is abandoned
- We want to take the code in a new direction
- We need a stable dependency version unaffected by upstream changes

---
## Fork_vs_Clone

| Aspect | Fork | Clone |
| --- | --- | --- |
| Location | **Github** (remote, our account) | Local machine |
| Write access | Yes (to our fork) | Only if you own the original repo |
| Used for | Contributing via PRS, maintaining versions | Local development, testing |
| Required for Open-source contribution? | ✅ Yes (if not a collaborator) | No, but often used after forking |

## Upstream_Tracking

When we push a new branch for the first time. We don’t need to type the remote or branch name anymore.

```bash
git push -u origin feature/awesome
```

**`-u`** = sets upstream so next time:

```bash
git push
git pull
```
