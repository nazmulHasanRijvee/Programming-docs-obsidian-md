Some classes refuse to pick a side; they expose their data through getters and setters but they also have methods that do real work.

Like this **`Product`** class, it lets anyone read and write the price but it also calculates discounts. So, when a **`Subscription`** class comes along with different pricing the discount logic is trapped inside this class

And when we need new behavior (methods) like calculating total price (according to quantity) or tax the data is already leaked because we have to use the getters everywhere

It becomes half data structure and half object. This called a **Hybrid** which is the worst of both worlds.

```python
class Product:
    __name = ''
    __price = 0.0

    def get_name(self):
        return self.__name
    def get_price(self):
        return self.__price

    def set_name(self, price):
        self.__price = price

    def apply_discount(self, pct):
        return self.__price * (1 - pct/100)

class Subscription:
    __monthly = 0.0
    __months = 0

    def apply_discount(self):
        if self.__months > 12:
            return self.__monthly * 0.8
        return self.__monthly


p = Product()
qty = 10
rate = 0.2

total = p.get_price() * qty # Data leaked
tax = p.get_price() * rate
```

A pure Data Structure doesn’t have this problem. We have to put the business logic somewhere else like another class specifically for business logic or behavior.

Remember Objects hide data and expose behavior where Data Structure expose data and skip behavior

```python
class Product:
    __name = ''
    __price = 0.0

    def get_name(self):
        return self.__name
    def get_price(self):
        return self.__price

    def set_name(self, price):
        self.__price = price

class ProductPricing:
    def apply_discount(self, product = Product(), pct = 0.0):
        return product.get_price() * (1 - pct/100)
```
