Follow these always:

## Centralization

Instead of writing the same thing multiple times, write once in a separate place and use it anywhere. Like one central static variable for magic strings (**`"Hi, ..."`**) or storing KEYs of a **Map** to prevent typing mistakes in future (One less risk, **`enum`** is used too). So, changing it only in one central point instead of everywhere. This is centralized control

---
## Reusability

If same code, same logic, same variable, and same widget is used multiple times or duplicated. Then make it reusable using a function or method, Class, and extracting widget etc. So, we have centralized control, prevented duplication and reduced extra boilerplate code or spaghetti. Use state hoisting, constructor parameters, a bool value to ensure reusability, or using an **`enum`** as a replacement of static const variables

---
## Readability

Don’t overengineer things. If something can be done using a simple approach then do it simply, don’t add complexity. Make sure other developers can read the code and understand it easily. But if the simple approach makes it harder to understand then drop it. The number one priority is Readability because after six months the next developer who reads the codebase might be you! Use proper yet short comments, ensure [Reusability](#Reusability) and [Breaking into Small Chunks](#Break_into_Small_Chunks) approach

---
## Break_into_Small_Chunks

Even if code, variables, Class, function, and widgets are not reusable, but still Break it into Smaller Chunks. Like custom widgets or splitting build methods. This keeps the Widget Tree small, increasing code Readability and better understanding

---
## Reduce_Code

More code = More Liability, leading more time for debugging. Number of lines of code doesn’t mean good code, it just means more to read for debugging. Try to implement logic or do something by writing as few lines of code as possible. But don’t make it too complicated so it loses Readability. Maintain Readability while writing less code

---
## Backtracking_Flow_for_Debugging

Software engineer thinks in inverse (what to do when opposite of the condition is true) or in reverse. Like thinking the opposite or inverse of the condition and what to do (**`if(!codition) return)`**) this ensures less code, less **`if-else`** nesting and increases Readability. Same approach is for Backtracking, if we face bug instead of debugging from where the Code Flow is starting, debug from where the Code Flow ends with result and go in reverse. This way we can spot bugs more easily.
