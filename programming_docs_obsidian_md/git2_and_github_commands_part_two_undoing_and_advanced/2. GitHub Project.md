GitHub Projects is a flexible, spreadsheet-meets-Kanban task management tool that lives inside GitHub.

Key insight, unlike Trello or Jira, GitHub Projects doesn't just link to our code but it IS part of our code infrastructure. Issues and PRs from our repos become "cards" in the board automatically.

Three core things it gives us:

- Board view: visualize tasks as columns (Backlog → In Progress → Done)
- Table view: spreadsheet-style view of all items with custom fields
- Roadmap view: timeline/Gantt-style view for planning sprints

## Importance(Why_use_it)

Real developers use GitHub Projects because:

- Without it: We have issues scattered across repos, no idea what's being worked on, team members stepping on each other's work, no sprint planning.
- With it: One source of truth. Automated workflows. Linked directly to the actual PRs and commits doing the work.

The killer feature, when we close a PR, the linked issue can automatically move to "Done" on our board. Zero manual updating.

## Usage(Step-by-Step)

##### Step 1, Create a Project

Go to our GitHub profile or organization → click "Projects" tab → "New Project". We'll be asked to choose a template:

- Team backlog → good starting point
- Kanban → classic columns
- Blank → full custom control

##### Step-2, Add our repos to it

Inside our project → Settings → "Linked repositories" → add our repos. This tells GitHub: "pull issues and PRs from these repos into this project."

##### Step-3, Add issues as items

There are two ways:

- Way 1: From the board: click + Add item at the bottom of any column → type # → search for an issue or PR from our linked repo.
- Way 2: From the issue itself: when you create or view an issue, look for the "Projects" section on the right sidebar → click the gear → select our project.

##### Step-4, Create Custom Fields

This is where Projects v2 becomes powerful. First in the Project, create another view (View 2) by clicking on the + icon next to the View 1 and in layout select Table

Then in Table View scroll all the way right on the header row and click the + icon at the end (in table view) to add:

- Priority → Name it Priority and set field type to Single Select, then add options like:
  - P0 (Critical, must ship now)
  - P1 (High priority, this sprint)
  - P2 (Nice to have, next sprint)
- Sprint → Iteration field (GitHub auto-manages 2-week sprints)
- Story points → Number field
- Due date → Date field

Finally, click on view settings and save view

##### Step 5, Set up automation

Go to our project → "..." menu → "Workflows" → we'll see built-in automations:

```text
When: Issue closed
Then: Set status to "Done"

When: PR merged
Then: Set status to "Done"

When: Issue opened
Then: Set status to "Backlog"

When: PR opened
Then: Set status to "In Progress"
```

These are toggle-on automations like one click to enable. No code needed.

##### Step-6, Linking issues to PRs (The Real Workflow)

This is how it works in practice on a real project:

- We create an issue:

  ```text
  Issue #42: Add login screen UI in Flutter
  ```

- We create a branch using git command:

  ```bash
  git checkout -b feat/login-screen
  ```

- We write our code, then open a PR with this in the description:

  ```text
  Closes #42
  ```

That Closes #42 is magic. When the PR merges, GitHub automatically closes issue #42. And if we have automation set up, it moves the card to "Done" on our board.

The full list of keywords GitHub recognizes; all do the same thing:

```text
close #1
closes #1
closed #1
fix #1
fixes #1
fixed #1
resolve #1
resolves #1
resolved #1
```

Don’t do this. It’s wrong and only closes #1 (issue)

```text
Closes #1, #2, #3
```

Right way, closes all three

```text
Closes #1
Closes #2
Closes #3
```

## The_Flow_in_our_Board

- Issue #42 starts in Backlog
- → We start working: manually drag to "In Progress" (or automation on PR open)
- → PR opened for review: moves to "In Review"
- → PR merged: automatically → "Done", issue closed

## Common_Mistakes

- Mistake-1, Treating it like Trello (manually managing everything). Projects shine when we link issues and PRs. If we're creating "draft notes" instead of real issues, we lose all the automation power.
- Mistake-2, Not using the "Closes #N" keyword in PRs. Most beginners write PRs without linking them to issues. This breaks the automation chain completely.
- Mistake-3, One giant project for everything. Teams with 5+ repos often put ALL work in one board with no filtering. Use views (saved filters) inside our project to show only "Flutter issues" or "this sprint's work."
- Mistake-4, Ignoring the Roadmap view. Solo devs never touch it. But when we start planning features across weeks, the roadmap view (with iteration fields) is how senior devs think about scope.
- Mistake 5, Not setting up workflows. The default project has automation OFF. Most beginners drag cards manually every day like it's 2010. Turn on the built-in workflows on day one.

## Industry_Practices

In real teams at product companies:

- Sprint planning uses the Iteration field, GitHub auto-creates 2-week iterations and we drag issues into the current sprint
- Priority triage happens weekly and filter by Priority: P0 and make sure those are all "In Progress"
- GitHub Actions + Projects API, advanced teams use the GraphQL API to programmatically move cards, create issues, or generate weekly reports
- Sub-issues (new in 2024) GitHub now supports breaking one issue into sub-tasks directly inside the issue, replacing the old checkbox hack
- Milestones vs Projects, Milestones are for version-based releases (v1.0, v2.0). Projects are for ongoing workflow management. Senior dev’s use both together
