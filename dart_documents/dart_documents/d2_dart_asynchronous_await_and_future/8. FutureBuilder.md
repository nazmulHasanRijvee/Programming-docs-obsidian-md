In **Flutter**:

- API calls
- Database reads
- **`SharedPreferences`** reads
- File loading

All of these return a **`Future`** and UI cannot wait synchronously. **`FutureBuilder`** listens to a **`Future`** and rebuilds the UI automatically when the **`Future`**’s state changes.

It takes a type **`FutureBuilder<T>()`** to know the return type.

**`future:`** takes a **`Future<T>`** function like API call or **`async`** calls. It can be **`null`**

**`snapshot`** represents the current state of the **`Future`**.

- **`snapshot.connectionState`** → loading / done
- **`snapshot.data`** → result (if success)
- **`snapshot.error`** → error (if failed)
- **`snapshot.hasData`** → data exists
- **`snapshot.hasError`** → error exists

**`snapshot.connectionState`** possible values:

- **`none`** → Future is null
- **`waiting`** → Future is running
- **`active`** → (mostly streams)
- **`done`** → Future completed

For **`FutureBuilder`**, we mostly use **`.waiting`** and **`.done`**

```dart
FutureBuilder<Weather>(
  future: weatherService.getWeather(),
  
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return const CircularProgressIndicator();
    }
    
    if (snapshot.hasError) {
      return Text('Error: ${snapshot.error}');
    }
    
    if (!snapshot.hasData) {
      return const Text('No data');
    }
    
    final weather = snapshot.data!;
    
    return Text('${weather.temperature}');
  },
)
```

> **NOTE:** There’s also **`initialData:`** the data that will be used to create the snapshots provided until a non-null future has completed. Also **`child:`** parameter is available for optimization

---
## Where_to_create_the_Future

Don’t assign the **`Future<T>`** API call directly because it will call the API every time when it gets built instead define a **`late Future`** function type variable. This way we can prevent multiple API calls.

```dart
late Future<Weather> weatherFuture;
@override
void initState() {
  super.initState();
  weatherFuture = getWeather();
}
FutureBuilder(
  future: weatherFuture,
)
```

---
## Important

**`FutureBuilder`** vs **`initState`** + **`setState`**. Using **`FutureBuilder`** when:

- Simple one-time load
- UI directly depends on Future
- No complex State Management

Using **`initState`** + **`setState`** when:

- Multiple async calls
- Manual control
- Complex logic
- Caching

---
## Refreshing_a_FutureBuilder

Just call the Future API caller again in the late variable in **`setState`** and we can wrap inside **`RefreshIndicator`**’s **`onRefresh`** callback if we want to

```dart
setState(() {
  weatherFuture = getWeather();
});
```

---
## Handling_empty_and_error_UI_cleanly

```dart
if (snapshot.hasError) {
  return ErrorWidget(snapshot.error!);
}
if (!snapshot.hasData) {
  return const Text('Nothing found');
}
```

---
## Common_mistakes(avoid_these)

- Calling `Future<T>` function inside **`build()`**
- Ignoring **`snapshot.hasError`**
- Not handling loading state
- Multiple API calls unintentionally
- Using **`setState`** with **`FutureBuilder`** data
