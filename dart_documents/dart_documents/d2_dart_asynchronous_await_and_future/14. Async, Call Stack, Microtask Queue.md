`async` is Single Thread meaning uses the Event Loop to handle tasks without blocking the main thread. Code flow:

**Step-1**, here main thread starts `fetchUser()` method, in that method:

- `await` registers the timer or continuation Callback and pauses the `fetchUser()` method until the continuation Callback returns completed result

- Only after that it resumes (so thread is free after registering the Callback). So, `await` does not stop the thread, it only pauses the current async function (`fetchUser()`). It basically says "Okay, resume this function later. I'm going to continue executing other available work now."

**Step-2**, then immediately **Dart** runtime & Event Loop, runs:

- **`fetchPosts()`** method until **`await Future.delayed()`**
- Pauses and registers continuation callback, thread is free again

**Step-3**, prints ‘End’ and this is why ‘End’ is printed first than the first two methods

Mental Model:

```text
main()
├─ fetchUser()
│    └─ await ...
│       ↳ pause function
│       ↳ register continuation callback
├─ fetchPosts()
│    └─ await ...
│       ↳ pause function
│       ↳ register continuation callback
└─ print("End")
```

Output:

```text
End
```

At this point:

```text
fetchUser()  -> paused
fetchPosts() -> paused
main()       -> finished
```

Then the flow in Callback queue becomes:

```text
Timer/Network completes // awaited operation completes
        ↓
Callback placed in queue // Continuation callback added to queue
        ↓
Event loop picks it up // Event Loop picks callback & resumes it
        ↓
Resume fetchPosts() // async function resumes after await
```

Think of `await` as “Pause me here. **Event Loop** Call me back when the result is ready. Meanwhile, continue with other work”. It’s like we don’t order the food & wait for it, we simply do other work and when the food is ready, it’s served

The **Event Loop** takes the continuation Callback results from a queue (line) so the first completed result gets executed first.

> **NOTE:** VERY IMPORTANT, Event Loop only takes the next task when the [Call Stack](#Call_Stack_in_Event_Loop) is empty

Code:

  print("End");

## Call_Stack_in_Event_Loop

The **Call Stack** is not a to-do list but its “The chain of functions or nested functions currently being executed”.

Event loop generally runs one thing at a time using a **Call Stack**, it means:

- **Step-1**, `main()` starts so **Call Stack** is:

  ```text
  ┌──────┐
  │ main │
  └──────┘
  ```

- **Step-2**, `main()` calls `functionA()` and notice `main()` is not finished, waiting for `functionA()`. So, **Call Stack** now:

  ```text
  ┌───────────┐
  │ functionA │
  ├───────────┤
  │   main    │
  └───────────┘
  ```

- **Step-3**, `functionA()` calls `functionB()`. Now `functionB()` is on top and The CPU always executes the top frame like a Stack. The **Call Stack**:

  ```text
  ┌───────────┐
  │ functionB │
  ├───────────┤
  │ functionA │
  ├───────────┤
  │   main    │
  └───────────┘
  ```

- **Step-4**, `functionB()` executes and finishes. Pop stack:

  ```text
  ┌───────────┐
  │ functionA │
  ├───────────┤
  │   main    │
  └───────────┘
  ```

- **Step-5**, `functionA()` finishes. Pop:

  ```text
  ┌──────┐
  │ main │
  └──────┘
  ```

- **Step-6**, `main()` finishes. Stack:

  ```text
  (empty)
  ```

This is why its LIFO (Last in First Out), think of function calls like this:

```text
main
 └─ functionA
      └─ functionB  ← currently running
```

Before `functionA` can continue, `functionB` must finish. Before `main` can continue, `functionA` must finish. So, the most recently called function is always the one currently executing (Stack works perfectly for this)

### Relation_to_Event_loop

When an **`async`** function reaches:

```dart
await Future.delayed(...);
```

Something special happens. Before await Call Stack:

```text
┌───────────┐
│ fetchUser │
├───────────┤
│   main    │
└───────────┘
```

With it, at await:

- Register continuation callback.
- Pause the function.
- Remove `fetchUser()` from stack.

Call Stack becomes:

```text
┌──────┐
│ main │
└──────┘
```

Later when `main()` finishes Call Stack:

```text
(empty)
```

The Event Loop now waits (after doing other work like finishing `main()`). REMEMBER, Event Loop only takes the next Callback or task from the queue only when the Call Stack is empty. Now, when the Future completes:

```text
Callback Queue     // Call Stack empty
      ↓
Event Loop
      ↓
Resume fetchUser
```

The runtime pushes the continuation Callback from the queue to the Call Stack:

```text
┌───────────┐
│ fetchUser    │
└───────────┘
```

and execution continues after the await part in that function. This is how Call Stack, Event Loop, Microtask Queue, Continuation Callback queue interacts and await just marks it.

## Microtask_Queue

**Dart**’s **Event Loop** has two queues to pick from:

- Microtask Queue ← High priority
- Event Queue ← Low priority

Event is basically `Future()`, `Future.delayed()` without **`async/await`**

### Microtask_Impact

Without Microtasks imagine only one queue (Event queue) where Event Loop takes first event and executes it.

With Microtasks **Dart** does this:

```text
Microtask Queue
---------------
M1
M2
Event Queue
-----------
E1
E2
E3
```

**Event Loop** rule, so Microtasks always run before normal events (continuation Callbacks):

1. Execute current stack   // **Callback Stack** empty?
2. Empty ALL microtasks
3. Execute ONE event // `Future()` or `.delayed()` without `async/await`
4. Empty ALL microtasks
5. Execute ONE event
6. Repeat

Then Full Mental Model:

```text
Single Thread
      │
      ▼
 Call Stack
      │
      ▼
Stack Empty?
      │
      ▼
┌─────────────────┐
│ Microtask Queue │  ← highest priority
└─────────────────┘
      │
      ▼
┌─────────────┐
│ Event Queue │  ← Future(), timers, Future.delayed() I/O, UI events
└─────────────┘
      │
      ▼
  Event Loop
```

### Code_Example

**Step-1**, `print(“Main”)` runs because its synchronous and in the **Call Stack** which is must be empty before **Event Loop** picks tasks from other two queues

**Step-2**, after printing main, Call Stack becomes empty and Event Loop has two queues to pick from:

```text
Microtask Queue
---------------
Microtask
Event Queue
-----------
Future
```

**Step-3**, Event Loop checks any Microtasks? If yes then run them all before Event or continuation Callback queue. So, prints microtask

**Step-4**, finally Microtask queue is empty. Now run one event or continuation Callback from the queue. So, prints future

```dart
void main () async {
Future(() => print("future"));
scheduleMicrotask(() {
  print("microtask");
});
print("main");
```

Output:

```text
main
microtask
future
```

### async/await_Continuation_Callback_with_Microtask

This is the interesting part. When a **`Future`** or continuation Callback completes or returns a result:

```dart
await something();
```

The continuation or resuming after the **`await`** is typically scheduled as a microtask. Conceptually:

```dart
await fetch();
print("Done");
```

Becomes something like the below, and that continuation or resuming gets very high priority:

```dart
fetch().then((_) {
  print("Done");
});
```

That's one reason **`async`** code often resumes before timers and other events.

> **NOTE:** **JavaScript** or **TypeScript** also has these **Call Stack**, **Microtask queue**, **Event queue**
