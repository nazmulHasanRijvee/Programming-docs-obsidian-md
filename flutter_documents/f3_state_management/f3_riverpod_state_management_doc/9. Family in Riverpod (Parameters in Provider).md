#### Definition:
\# Family in **Riverpod** lets one Provider create multiple independent **states** (data) based on parameters like:

- User Profile (**userId**)
- Search (**query**)
- Pagination (**page**) and Product Details (**productId**)

\# Family Provider is like a **Map<Key, Value>**

---

#### The_Problem_Family_Solves:
\# Suppose we have an API:

**GET /users/1**
**GET /users/2**

\# Without Family, we might end up creating Providers like this:

```dart
final user1Provider = AsyncNotifierProvider(...);
final user2Provider = AsyncNotifierProvider(...);
```

\# This obviously doesn’t scale. Instead, we want one Provider that accepts a parameter like a function. Instead of **int getAgeOfJohn()** we write **int getAge(String name)**

\# Now one function works for everyone. Family does exactly this for Providers

---

#### Mental_Model:
\# Think of a normal Provider as a variable which has one **state** (value)

**counterProvider**
**↓**
**0**

```dart
final counterProvider = Provider((ref) => 0);
```


\# Think of Family as **Map** where the parameter (**userId**) is the Key and the Provider’s **state** (data) is the Value. We aren’t creating many Providers ourself, **Riverpod** creates them internally

```ASCII
userProvider
↓
{
   1 : User(...)
   2 : User(...)
   3 : User(...)
}
```


\# For example, on **ref.watch(userProvider("1"))** called **Riverpod** internally behaves as if it created **Provider(User 1)**. Later when **ref.watch(userProvider("2"))** is called **Riverpod** creates another independent instance **Provider(User 2)** so internally they never interfere with each other

---

#### Basic_Syntax:
\# Use the **.family<…, …>()** constructor of **Provider** when defining it. The **.family<User, String>()** generics means return -> **User** and accepts parameter-> **String**

\# Suppose our `AsynNotifier<T>` looks like this, takes the parameter in the constructor of the Notifier class and use it. Make sure its positional not **required** or named parameter

```dart
class UserNotifier extends AsyncNotifier<User> {
  UserNotifier(this.id);
  final String id;

  @override
  Future<User> build() async {
    final dio = Dio();
    final response = await dio.get('https://api.example.com/users/$id');
    return User.fromJson(response.data);
  }
}
```


\# (Alternative) Or extend **FamilyAsyncNotifier<…, …>**. Here, generic means returns -> **User** and accepts parameter -> **String**, so no constructor or variable initialization needed. The Family parameter is received by **build(…)** method

```dart
class UserNotifier extends FamilyAsyncNotifier<User, String> {
  @override
  Future<User> build(String id) async {
    return repository.getUser(id);
  }
}
```


\# Now with Family the **AsyncNotifierProvider**

```dart
final userProvider =
    AsyncNotifierProvider.family<UserNotifier, User, String>(
       UserNotifier.new,
       isAutoDispose: true
);
```


\# In the UI, instead of **ref.watch(userProvider)** use the below, where every parameter creates an independent Provider instance

```dart
final user1 = ref.watch(userProvider("123"));
// Or
final user 2 = ref.watch(userProvider("987"));
```

---

#### Family + AutoDisopse:
\# It’s strongly recommended to enable automatic disposal with Families. Otherwise, if users keep requesting different parameters (search queries, page numbers, IDs), **Riverpod** may retain Provider instances that are no longer needed (SEE Auto Disposal Below)

```dart
final userProvider =
    AsyncNotifierProvider.family<User, String>(
      UserNotifier.new,
      isAutoDispose: true,
    );
```

#### Family_with_Every_Provider_Type:
##### 1. FutureProvider:
```dart
Future<User> getUser(String id) {…} // Repository
final userProvider =
    FutureProvider.autoDispose.family<User, String>((ref, id) async {
  return repository.getUser(id);
});
```


##### 2. StreamNotifer:
\# Perfect for chat rooms:

```ASCII
Room A             Room B
  ↓                  ↓
messages...       messages...
```

```dart
class ChatNotifier extends FamilyStreamNotifier<List<Message>, String> {
  @override
  Stream<List<Message>> build(String roomId) {
    return repository.messages(roomId);
  }
}
// Family with Provider
final chatProvider =
    StreamNotifierProvider.family<ChatNotifier, List<Message>, String>(
      ChatNotifier.new,
      isAutoDispose: true
    );
```


\# In UI, now each room has its own Stream

```dart
ref.watch(chatProvider("flutter"));
ref.watch(chatProvider("riverpod"));
```


##### 3. Notifier:
\# `Notifier<T>` is the same as `AsyncNotifier<T>`

#### Parameter_Rules:
\# Our parameter must have stable `==` (equal method) and **hashCode**, because **Riverpod** uses it as the key to store it in the **Map**

\# Like Good ones:
- **userProvider("123");**
- **productProvider(42);**
- **localeProvider(Locale("en"));**

\# BAD practice is:

```dart
ref.watch(myProvider([1, 2, 3]));
```


\# Each time we create a new **List**, it's a different object in memory:
**[1,2,3] != [1,2,3]**

\# **Riverpod** thinks they're different keys and creates different Provider instances. (BE AWARE) recommend using immutable objects with consistent equality

---

#### Accessing_All_Active_Providers_of_a_Family:
\# Using **ProviderContainer()**/**ProviderScope()**, we can access all the Providers that are linked to a Family thanks to its **.allProviders** method:

```dart
for (final reference in ref.container.allProviders(family: userProvider)) {
  ref.invalidate(reference.provider);
}
```

#### Overriding_Families:
\# When trying to mock a Provider in tests, we may want to **override** a Family Provider. In that case, we have two options:

##### 1. Override only a specific parameter combination:
```dart
await tester.pumpWidget(
  ProviderScope(
    overrides: [
      userProvider('123').overrideWith((ref) => User(name: 'User 123')),
    ],
    child: const MyApp(),
  ),
);
```


##### 2. Override all parameter combinations:
```dart
await tester.pumpWidget(
  ProviderScope(
    overrides: [
      userProvider.overrideWith((ref, arg) => User(name: 'User $arg')),
    ],
    child: const MyApp(),
  ),
);
```
