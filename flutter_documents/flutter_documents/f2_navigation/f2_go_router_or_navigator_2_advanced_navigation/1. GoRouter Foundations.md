The three pieces that work together in every **go_router** app:

| Piece                | What it actually is                                                                                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GoRouter`           | The router configuration object that holds our route tree, and implements **Flutter**'s Router API internals for us                                |
| `GoRoute`            | One entry in that tree which maps a URL path to a widget builder                                                                                   |
| `MaterialApp.router` | A special constructor of `MaterialApp` that accepts a `routerConfig` instead of a home widget. This is how we plug `GoRouter` into the widget tree 

---
## Why Use it:
Navigator 2.0 on its own is brutal to use directly. To use raw Router API, we must hand implement three abstract classes ourself:

- `RouterInfromationProvider`  -> listens for URL/deep-link changes from the OS or browser
- `RouterInformationParser` -> turns a raw URL string into our own app-defined “route state” object
- `RouterDelegate` -> takes that route state and builds the actual Navigator widget with the correct page stack

Writing these three by hand for a real app is 200+ lines of boilerplate code. **go_router** is pre-built implementation of all three, exposed through a declarative `routes:` List. It’s just Navigator 2.0 with the boilerplate surgically removed

---
## Mental Model
 We never touch `RouteInformationParser` or `RouterDelegate` directly. We declare `routes:`, and `GoRouter` wires the rest. When we later hit redirect, `refreshListenable:` , or `errorBuilder:` those are just hooks `GoRouter` exposes into this internal pipeline

```text
                    ┌─────────────────────────────────────────┐
                    │              GoRouter                   │
                    │  (implements all 3 Router-API pieces)   │
                    │                                         │
  OS / Browser       │  ┌──────────────────────┐               │
  URL change   ───▶│   │ RouteInformationParser│             │
  or context.go()    │  └──────────┬───────────┘               │
                    │             ▼                           │
                    │      matches against your                │
                    │      routes: [GoRoute, GoRoute, ...]    │
                    │             │                           │
                    │             ▼                           │
                    │  ┌──────────────────────┐               │
                    │  │    RouterDelegate     │              │
                    │  └──────────┬───────────┘               │
                    └─────────────┼───────────────────────────┘
                                  ▼
                     Navigator(pages: [HomePage, DetailsPage])
                                  │
                                  ▼
                          rendered on screen
```

## Properties of GoRouter() & GoRoute():
`GoRouter()` class (the router itself) has properties for configuration like:

- `routes:` -> takes the list of `GoRoutes` or our entire route tree
- `initialLocation:` -> where the app starts if there's no deep link (defaults to **/**)
- `debugLogDiagnostics:` -> prints every route match/parse to console (easier debugging)
- `errorBuilder:` -> Fallback screen when no route matches (SEE )

`GoRoute()` class (one entry in the route tree):

- `path:` -> the URL segment this route matches (:id = param, SEE BELOW)
- `builder:` -> the widget or page to build for that path. Internally gives us `BuildContext` -> and `GoRotuerState` instances. It automatically wraps our widget or screen in a `MaterialPage()` (or `CupertinoPage()`) for default transitions
- `pageBuilder:` -> used when we need custom transitions (SEE BELOW) instead of wrapping in `MaterialPage()`
- `routes:` -> for nested child `GoRoutes` (SEE BELOW)

## Basic Usage
`routerProvider` for Singleton Pattern (using **Riverpod**) instance of `GoRouter()`, created only once

`routes: [GoRoute(path: '/', ...)]` a single route for the root path. `state` is a `GoRouterState` used for path/query params (SEE BELOW)

In `MaterialApp.router(…)` there is no `home:` param anymore instead the router decides what's on screen

```dart
final routerProvider = Provider<GoRouter>((ref) {
   return GoRouter(
      initialLocation: '/',
      debugLogDiagnostics: true,
      routes: [
         GoRoute(
             path: '/',
             builder: (context, state) => const HomeScreen(),
         ),
      ],
   );
});

class MyApp extends ConsumerWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final router = ref.watch(routerProvider);

    return MaterialApp.router(
      routerConfig: router,
      // ...
    );
  }
}
```

## Industry Practices
Pattern-1, use **go_router_linter** package for code quality

Pattern-2, Single source-of-truth file **router.dart**. Define the tree in one file. Instead of scattering route definitions across the codebase makes it difficult to reason about navigation flow, with a single **router.dart** file acting as a map of the entire app

Pattern-3, Never hardcode route strings. Like any raw `'/profile'` string in a `context.go()` call or `GoRoute()` definition. Use a static constant or enum instead

Pattern-4, keep the `GoRouter()` instance stable via DI, using **Riverpod** or **get_it**, so it survives widget rebuilds and can be swapped/mocked in tests
