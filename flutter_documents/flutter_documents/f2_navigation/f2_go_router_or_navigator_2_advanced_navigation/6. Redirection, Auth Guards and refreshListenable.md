- **`redirect:`** -> a callback (on **`GoRouter()`** or on an individual **`GoRoute()`**) that intercepts a navigation and reroutes it based on app state
- **`refreshListenable::`** -> a **`Listenable`** and when it fires, makes **`GoRouter()`** re-run redirect logic against wherever the user currently is. Without them navigating anywhere

---
## Why_Use_It

Without this, we'd have to put an

```dart
if (!isLoggedIn) return LoginScreen();
```

check inside every protected screen's **`builder:`** which causes duplication. **`redirect:`** centralizes access control in one place in our router config, evaluated before any screen builds.

But **`redirect:`** alone doesn't solve, what happens if the user's auth state changes while they're sitting on a screen like token expires, or a login completes on a separate screen? **`redirect`** only runs on navigation events.
 
 **`refreshListenable`** is the bridge that lets a state change itself trigger a re-check.

---
## Mental_Model
IMPORTANT, **top-level runs first, on every single navigation, no exceptions.** Route-level only fires for the specific route it's attached to, and only after the top-level check has already passed.

```text
Navigation event (context.go, deep link, OR refreshListenable fires)
                         │
                         ▼
          top-level redirect (GoRouter constructor)
             called first, for EVERY navigation
                         │
                   null? ─┴─ returns a path?
                    │              │
                    ▼              ▼
     route-level redirect     reroute there,
     (on the matched GoRoute)  re-run from the top
     for the matched path          (up to redirectLimit times is by
                    │                default 5, else error screen)
              null? ─┴─ returns a path?
               │              │
               ▼              ▼
          screen builds   reroute, re-run
```

## Basic_Usage

**`GoRouter(redirect: ...)`** ->  the top-level  `(BuildContext, GoRouterState) => String?` which is checked before every navigation

**`GoRoute(redirect: ...)`** ->  the Route-level one, same signature, but scoped to that one **`GoRoute()`**

**`redirectLimit: `** -> Max redirect chain length before **go_router** shows an error screen instead of looping forever (defaults to **`5`**)

**`refreshListenable:`** -> A `Listenable` (typically a **`ValueNotifier<T>`** or  **`ChangeNotifier`**) and firing it re-evaluates **`redirect:`** at the current location

**`GoRouterRefreshStream`** -> Helper class that adapts a **`Stream`** (e.g. **Firebase's** **`authStateChanges()`**) into a **`Listenable`** for **`refreshListenable`**

Here, **`!loggedIn && !goingToLogin`** catches "unauthenticated user trying to reach a protected page" → send to **`/login`**.

**`loggedIn && goingToLogin`** catches the inverse like an already-logged-in user hitting `/login` directly → bounce them to `/home` instead. Both checks explicitly **exclude** `/login` itself from the "must be logged in" rule to ensure idempotency ( prevents an infinite loop)

```dart
class AuthNotifier extends ChangeNotifier {
  bool isLoggedIn = false;

  void login() {
    isLoggedIn = true;
    notifyListeners(); // this is what wakes refreshListenable up
  }
}

final authNotifier = AuthNotifier();

final GoRouter _router = GoRouter(
  initialLocation: '/home',
  
  refreshListenable: authNotifier,
  
  redirect: (BuildContext context, GoRouterState state) {
    final loggedIn = authNotifier.isLoggedIn;
    final goingToLogin = state.matchedLocation == '/login';

    if (!loggedIn && !goingToLogin) return '/login';
    if (loggedIn && goingToLogin) return '/home';
    return null; // no redirect needed
  },
  
  routes: [
    GoRoute(path: '/login', builder: (context, state) => const LoginScreen()),
    GoRoute(path: '/home', builder: (context, state) => const HomeScreen()),
  ],
);
```

---
## Important_Concepts

**`refreshListenable`** is what makes **`authNotifier.login()`** actually take effect. Without it, calling **`login()`** updates the boolean, but the router has no idea anything changed so the user stays stuck wherever they were until they trigger a separate navigation event. With it, **`notifyListeners()`** directly causes **`redirect`** to run again at the current location, and the login → home bounce happens immediately.

**Route-level** (**`GoRoute()`**) **`redirect:`** only fires once its route is the top-most matched route. if we redirect from a parent route to somewhere entirely different, child route-level redirects on the original branch never get a chance to run. KEEP in Mind

---
### Common_Mistakes

1. The infinite redirect loop -> If our redirect logic doesn't explicitly exclude the destination it's redirecting to, we get infinite loop the solution is shown above.
2. **`redirect:`** doesn't run on every **`setState()`** or **`build()`** in our app. Only on navigation events and **`refreshListenable:`** firings. If we're debugging "why isn't my redirect running," check it

### Industry_Practices

##### 1. `ChangeNotifier` + `GoRouterRefreshStream`

Wired to a real auth stream is the standard production pattern:
```dart
// ...
refreshListenable: GoRouterRefreshStream(FirebaseAuth.instance.authStateChanges())
```

so the router reacts automatically the instant **Firebase** reports a sign-in/sign-out, with zero manual **`notifyListeners()`** calls needed. In larger apps this **`ChangeNotifier`**/**Stream** is typically exposed through **Riverpod** or **get_it** through global DI

##### 2. `onEnter:`
In **go_router** version 16.3.0, added a global **`onEnter:`** callback as an evolution of **`redirect:`**, specifically designed for **`async`** guard checks

`redirect` must return synchronously, but `onEnter:` returns `FutureOr<OnEnterResult>` (`Allow()` or `Block()`), so it can `await` a network call (e.g., verifying a token server-side) before deciding.

#### 3. Router Guard Packages
There's also an actively maintained ecosystem of guard-composition packages (**go_router_guards**, **route_architect**) built specifically to chain multiple guard auth, then role check, then feature flag
